# NAVI companion: a design spec (not built)

This is a proposal for a fifth text route in Advanced → Languages, "NAVI companion". Nothing here is built. It's
written so anyone can pick it up; the parts marked "open" are decisions still to make.

## Why

On a non-English OS layout a keyboard can't type text correctly by itself: it sends key positions, so `@` from a
macro comes out as `"` on a Russian layout, and some characters are on no key at all. `docs/languages.md`
describes how NAVI routes that text today. The routes that exist each have a catch:

- **My own program**: the user writes C and a PC program. Fine for one person, out of reach for most users.
- **WinCompose**: needs the WinCompose app, and the keyboard can't tell when Windows switches language by itself
  (Win+Space, per-app layouts), so it drifts.
- **Windows Alt codes**: some apps ignore them, and Windows needs the `EnableHexNumpad` registry key.
- **Linux**: QMK's Unicode modes, Linux only.

A companion shipped with NAVI would give every Windows user the "own program" route without writing anything:
correct text in any language, and a keyboard that follows the OS when it switches layouts on its own.

## What the user sees

- In the Languages tab, the route "NAVI companion". Picking it offers to start the companion now and with Windows.
- A tray icon, no window. Its menu: the connected keyboards, a "Start with Windows" tick, Quit.
- Closing NAVI's window, or a dialog stuck open in it, never stops typing: the companion is its own process.
- Windows only. macOS and Linux keep the QMK Unicode routes.

## The process

- `NAVI.exe --companion` from the same install, with no window. It needs its own single-instance lock (for example
  its own `userData` path set before `requestSingleInstanceLock()`), since Electron's lock is per app and the window
  and the companion would otherwise block each other.
- Start with Windows: `app.setLoginItemSettings({ openAtLogin, args: ['--companion'] })`.
- It finds keyboards by the raw HID usage page and usage of the build (QMK's default `0xFF60` / `0x61`), sends
  HELLO to each, and keeps the ones that answer as NAVI keyboards. It reconnects when a keyboard comes back.
- It never needs the NAVI project file: everything it needs comes from the keyboard's HELLO answer.

## Protocol

Every packet is 32 bytes (on Windows a write is 33: a report id 0, then the packet). Byte 0 is NAVI's message
number, one value only, `0x4E`; byte 1 is the command. `0x4E` is clear of VIA's commands (`0x01`-`0x15`, `0xFF`)
and leaves room for more NAVI commands later (a "reboot into bootloader" for build + flash is planned on the same
byte).

| Byte 1 | Way | Payload (from byte 2) | Meaning |
|---|---|---|---|
| `0x01` HELLO | PC → keyboard | none | are you a NAVI keyboard |
| `0x01` HELLO | keyboard → PC | protocol version; current language index; count; then the language codes, NUL-separated | the answer |
| `0x02` TYPE | keyboard → PC | a piece of text in `send_string` format, NUL-terminated (at most 29 bytes) | type this, in order |
| `0x03` LANGUAGE | keyboard → PC | language index | switch the OS layout to it |
| `0x04` OS_LANGUAGE | PC → keyboard | language index | the OS switched; the keyboard follows (`navi_set_language`, nothing sent back) |
| `0x4B` `'K'` KEY COUNTS | both | `'I'` INFO or `'R'` READ, see below | built: the board route of “count key presses” |

TYPE's text format is the one in `docs/languages.md`: UTF-8 plus `0x01 0x01|02|03 <kc>` for key tap / down / up.
A piece never ends inside a UTF-8 character or a `0x01` sequence. The firmware already cuts text this way for VIA
macros (`NAVI_TEXT_PIECE` in `src/core/qmk/languages.ts`); the companion route uses the same cutter with a smaller
piece. A key pressed with `0x01 0x02` can stay down across pieces (a macro delay cuts the text).

Language codes are the short codes from the Languages tab (`en`, `ru`). Indexes are their order in the list.

## Firmware (generated by NAVI)

- A new `TextRoute` value `companion`. `navi_route_text()` sends TYPE pieces; `navi_switch_language()` sends
  LANGUAGE. No OS shortcut is tapped on this route.
- Who owns `raw_hid_receive` decides where the packet handler goes:
  - VIA off and no own code: NAVI generates `raw_hid_receive` and turns on `RAW_ENABLE`.
  - VIA on: NAVI defines `via_command_kb()`, which VIA calls before its own switch (`quantum/via.c`), handles
    `0x4E` packets there and returns true. A keyboard whose own code already defines `via_command_kb` can't use the
    route (a link error); NAVI should detect that in the QMK sources and say so.
  - Own pipeline: NAVI defines `bool navi_raw_hid_receive(uint8_t *data, uint8_t length)`, true when the packet was
    NAVI's; the user's `raw_hid_receive` calls it first. Document it beside the hooks in `docs/languages.md`.
- Must compile in real QMK with `-Werror` for all three owners, with and without VIA.

## Sharing VIA's channel

QMK builds one raw HID interface, so with VIA on the companion, NAVI's own window and the VIA app all see the same
reports (Windows gives every open handle a copy).

- NAVI's VIA client must skip `0x4E` reports instead of failing with "response for another command"
  (`src/core/via/client.ts`).
- The companion ignores every report that doesn't start with `0x4E`.
- A VIA app waiting for an answer could take a TYPE report for its answer. The tab warns: "shares VIA's channel:
  close the VIA app before typing outside English".

## What the companion does

These rules come from a private program that does the same job for one keyboard and has been in daily use:

1. **On connect** (after HELLO): send OS_LANGUAGE with the foreground window's current layout. The OS decides on
   connect: it's what's on screen.
2. **TYPE**: type at once on the HID reader's thread, never through a queue, so the user's next key (which goes
   straight from the keyboard to Windows) can't overtake it.
   - Text: `SendInput` with `KEYEVENTF_UNICODE`, one character at a time. Keys: their virtual keys.
   - Held modifiers: before typing, send key-ups for the modifiers Windows sees as down (Shift, Ctrl, Alt, Win,
     left and right); after, key-downs for the same ones. Before lifting Alt or Win, tap an unassigned virtual
     key (`0xE8`) so Windows doesn't take the lone Alt / Win up as "open the menu / Start".
   - Never write typed text to a log or history: passwords pass through here. Log lengths only.
3. **LANGUAGE**: switch the foreground window to the matching layout (`WM_INPUTLANGCHANGEREQUEST` with the
   layout's `HKL`).
4. **OS_LANGUAGE**: watch the foreground window's layout (its thread's `GetKeyboardLayout`, on foreground changes
   and layout changes) and send OS_LANGUAGE when it differs from the last language both sides agreed on.
   - A switch the companion made itself on LANGUAGE isn't reported back.
   - Wait for the layout to settle (about 300 ms after the last LANGUAGE) before comparing, so a quick ru-then-en
     on the keyboard doesn't report the passing `ru`.
5. **Matching codes to layouts**: by the layout's language id against the code (ISO 639-1, plus common aliases
   such as `ua` for Ukrainian).

Limits to state in the help text: `SendInput` can't type into a window running as administrator when the
companion isn't (Windows' UIPI), and some games read raw input and ignore injected text.

## Key counts (built, shares the byte)

“Count key presses” (Firmware → flash, for the heatmap) already uses `0x4E`, command `0x4B` `'K'`, and the same
`raw_hid_receive` / `via_command_kb` / `navi_raw_hid_receive` owners as the reboot packet: the generated hook tries
each NAVI handler in turn, so the companion's handler is one more entry there (`rawHidHookC` in
`src/core/qmk/bootloaderReboot.ts`). On the board route NAVI's own window reads the counts (`'I'` INFO: protocol,
table hash, count of counters; `'R'` READ `offset`: up to 13 counts, zeroed on the board as they are read); the
companion must ignore `0x4E 0x4B` replies it didn't ask for. The program route needs no packet: the firmware calls
`navi_key_count_user()` and a program of the user's own sends the counts wherever it likes (`docs/key-counts.md`);
a companion could take that job later and write the counts file itself.

## Tools (to confirm in a spike)

- **`koffi`** for the Windows calls (`SendInput`, `GetKeyboardLayout`, `GetKeyboardLayoutList`, `PostMessage`).
  Prebuilt for Electron. `ffi-napi` is unmaintained; a C++ addon needs build tools on every contributor's PC.
- **`node-hid`** in the companion's main process. The runner-up is WebHID in a hidden window, which reuses
  `src/device/webhid.ts` but keeps a renderer process running all day to read 32-byte reports.
- Both are native modules: electron-builder has to unpack them from the asar (`asarUnpack`). The first step is a
  spike that loads both in Electron 44 and in a packaged `npm run dist` build.

## Build order (riskiest first)

1. The spike above.
2. Firmware: the packet handler for the three owners, TYPE cutting and OS_LANGUAGE as host tests
   (`tests/qmk-host`), then the `-Werror` compile.
3. NAVI's VIA client skipping `0x4E`, tested with `src/core/via/simulator.ts`.
4. The companion: HID connect and reconnect, typing, the layout watch, tray, start with Windows. The input that
   `SendInput` gets can be unit-tested; the typing itself only by a person at the keyboard, since `SendInput`
   types into whatever window is in front.
5. The route in the Languages tab, starting the companion from NAVI, docs.

## Open

1. **No companion running, text outside English**: type nothing (the private program's choice; the missing tray
   icon is the visible sign), or fall back to plain keys (wrong characters on a non-Latin layout)?
2. **A language with no matching Windows layout installed**: its switch does nothing and the tray menu says
   "ru: no Windows layout installed"?
3. Does the HELLO answer need the keyboard's name for the tray menu, or is the USB product name enough?
